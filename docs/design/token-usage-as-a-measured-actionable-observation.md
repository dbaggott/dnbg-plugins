# Token usage as a measured, actionable observation

As-built design of https://github.com/dbaggott/claude-plugins/issues/654.

Section IDs (`C#`, `R#`, `D#`, `Q#`, `A#`) are the ones the children, PRs and commits cite, unchanged from the tracking issue, retired entries included. Problem and Constraints describe the plugin as it stood before this work, verified at `8e4b5b1`, and "today" in them means then.

Each role's close-out now records the usage of its run in its retrospective's frontmatter, a session owner also posts it on the issue as a `Usage:` comment, a sweep over the local transcripts attributes usage by agent, wake and plugin file, and `process-review` reports both by role against its previous report.

## Problem

Nothing in the workflow records what a run cost. The only guard that touches size is the byte cap on skill reference files in `tests/coupling.bats`, which prevents one failure, a lost read, and measures nothing about usage. A cap is also performed to: before https://github.com/dbaggott/claude-plugins/pull/643 raised it, 13 of 40 references sat between 10 and 12 KB against a 12,000-byte cap, and after https://github.com/dbaggott/claude-plugins/pull/651 set it from a measurement to 20,000, `multi-issue.md` sits 1,497 bytes under it.

The one measurement so far was a one-off audit on 2026-10-31 over 30 days of local transcripts. It found that cost is turns multiplied by context, with 65 percent of weighted cost in cache reads, and that an orchestrator's context grows past 150K on long runs. Its findings were filed as https://github.com/dbaggott/claude-plugins/issues/612 through https://github.com/dbaggott/claude-plugins/issues/619, https://github.com/dbaggott/claude-plugins/issues/621 and https://github.com/dbaggott/claude-plugins/issues/624, and https://github.com/dbaggott/claude-plugins/issues/615 shipped `scripts/context-size.sh`. The audit's scripts live outside the repo, nothing re-runs them, and nothing attributes usage to an issue or a role as runs happen. Whether 612 to 619 saved anything cannot currently be shown.

Each role already writes a retrospective at its close-out, read in batches by `process-review`. That loop records process friction per role per issue and is the natural carrier for usage, but it carries none, and `process-review` has no method for numbers.

## Goals

- Every close-out that writes a retrospective records the run's observed usage, in one fixed shape, by one rule that does not depend on how the role was invoked.
- Per-issue cost is visible on the issue itself, so sessions split by a restart or a separate reviewer session join by issue number.
- A sweep over local transcripts attributes usage by role, wake and file, is re-runnable from the installed plugin, and is tested on real scrubbed fixtures.
- `process-review` reads both, reports usage by role with a trend against its previous report, and drafts issues where the data warrants.

## Non-goals

- Reducing usage. That is 612 to 619 and their successors; this project measures whether they worked.
- Cost in currency. Records hold raw token counts; weighting, if any, happens in a report that names its weights.
- A per-PR size gate or ratchet on skill files, and any change to the reference cap, which https://github.com/dbaggott/claude-plugins/issues/647 settled.
- A scheduled or cloud runner. Transcripts are local files.
- Measuring sessions that never loaded a `dnbg-workflow` role.

## Requirements

### The usage record

- **R1.** A script in `dnbg-workflow/scripts/` prints the usage of the calling agent's own run as result lines in `context-size.sh`'s shape: `result=OK scope=<self|session> agent=<main|agentType> requests=<n> input=<n> cache_write=<n> cache_read=<n> output=<n>`, then for `scope=session` one `child=<agentType> id=<agent-id> depth=<spawnDepth> parent=<parentAgentId, or session at depth 1> requests=<n> input=<n> cache_write=<n> cache_read=<n> output=<n>` line per transcript under `subagents/`, at every depth; or `result=UNKNOWN reason=<no-session-id|no-transcript|no-nonce|no-match|ambiguous|parse>`. It never prints a guessed number. `requests` counts distinct `message.id` values among assistant entries carrying usage, and the four counts sum each such id's usage once (C15), taken from the last entry carrying that id, since an earlier entry can carry a partial `output_tokens` figure ([658-D1](https://github.com/dbaggott/claude-plugins/issues/658#issuecomment-6565452151)).
- **R2.** The script finds the caller's transcript by the two-call nonce of C5: a first invocation prints a fresh random nonce and nothing else; the second, given that nonce, greps the session's main transcript and every `subagents/*.jsonl` under it, and proceeds only on exactly one matching file; several lines of one file are one match, since a transcript repeats a tool result in `api-request-blob` entries. A match on the main transcript is `scope=session`; a match under `subagents/` is `scope=self` with `agent` read from the sibling meta file's `agentType`. The main transcript's `agent` is `main`.
- **R3.** `scope=session` totals the main transcript and every `subagents/*.jsonl` under it, at every depth. A `scope=self` record is the agent's own transcript only (D1), so the agents it dispatched appear only in the owner's `child=` lines, told apart by `depth` and `parent`, and the owner's own overhead is the total minus the `child=` lines.
- **R4.** The retrospective's frontmatter gains a `usage` mapping carrying the script's output, one key per field, named as the result line names them, so `agent` and never `role`, which stays the retrospective's own key, and a `children` list for `child=` lines; or `usage: {result: UNKNOWN, reason: <reason>}`. The four existing headings are unchanged.
- **R5.** The rule for writing it lives in `retrospective.md` alone and is one sentence for every role: at your close-out, run the script and record its lines in the frontmatter. No agent definition and no role's close-out text carries a rule that depends on whether the role was dispatched.
- **R6.** A close-out whose script reports `scope=session` also posts the `result=` and `child=` lines as a comment on the issue, under its own role, with the fixed first line `Usage:`. A `scope=self` close-out posts nothing, since its usage is inside its dispatcher's line. For a set of issues with no parent, the comment goes on the first issue of the retrospective's `issue:` list. A `Usage:` comment is not a review round: where a watch can wake on it, as `watch-issue.sh --role=author` can after a spec review, the skill text at that watch says a `Usage:` comment is no round and the author answers nothing.
- **R7.** The orchestrator's restart turn (C12), which today writes no retrospective, writes one with `role: orchestrator`, the usage frontmatter and the `Usage:` comment before its `**Your move:**` line, so a run split by restarts has one `Usage:` comment per session on the issue. The agents a restart cuts off leave no retrospective (`retrospective.md`, "Asking the agents for one"); their usage survives in that record's `child=` lines.
- **R8.** The retrospective's prompt gains a fifth heading, `## Read but not used`, for reference files or sections the agent read and did not need in this run, one per bullet naming the file, with `Nothing.` where none. `tests/coupling.bats:905`'s count and step 1's "four headings" become five. A retrospective without the heading stays readable and contributes nothing to R15, as step 1 already treats files written before a role became its own.

### The sweep

- **R9.** A sweep script, shipped under `dnbg-workflow/scripts/`, reads the main and subagent transcripts under the Claude Code config root for a date range, attributes each to an agent (`main`, or the meta file's `agentType`), and writes one report to `<retrospective root>/_usage/<YYYY-MM-DD>T<HHMMSS>Z.md` with a JSON twin. A main transcript is in scope when it holds a `Skill` tool use whose `skill` starts with `dnbg-workflow:`, or a tool use whose input names a path under the installed plugin (R19); a subagent transcript when its `agentType` starts with `dnbg-workflow:` or its session's main transcript is in scope. Whether the file mentions `dnbg-workflow` decides nothing (C6). The report gives, per agent, transcripts (its number of per-transcript rows, one per main session or subagent dispatch, so a session that dispatches three authors counts three for the author's agent type), requests (C15), the four counts and wakes (C16); per plugin file read, the read count (Q5, R19); per transcript, the same figures keyed by session ID, agent ID, depth and parent. The JSON twin's top-level keys are `range` (`since`, `until`), `ignored_reads`, `agents` (per agent: `transcripts`, `requests`, the four counts, `wakes`), `files` (plugin-relative path to read count) and `sessions` (one object per transcript: `session_id`, `agent_id` or null, `agent`, `parent`, `depth`, `requests`, the four counts, `wakes`).
- **R10.** *Retired 2026-11-01: a session-level exclusion also removed real usage, and the A1 run A2 must find (654-B11); superseded by R19.* The sweep excludes a session when any of its entries' `cwd` has the repository's name, the last path segment of `repository` in `.claude-plugin/plugin.json` (C17), as a path component, matched on the recorded string, so a worktree under the checkout is excluded and a directory since deleted needs no inspection; `--exclude-cwd=<component>` overrides the default. The report says how many sessions it excluded. (D7.)
- **R11.** The sweep is deterministic for a fixed input and date range, prints exactly one line, `result=OK report=<path>` or `result=UNKNOWN reason=<…>`, and exits 0, so a report it cannot write is `result=UNKNOWN reason=write` ([659 row](https://github.com/dbaggott/claude-plugins/issues/659#issuecomment-6565964981)), and is tested on fixtures captured from real transcripts in the manner of C11, reduced to the fields it reads and further: a Read `file_path` or a Bash `command` keeps only the plugin paths it names, each with its root replaced by a stand-in and its tail intact: `<config>` for a path under the installed plugin, keeping the tail from `plugins/cache/<marketplace>/dnbg-workflow/<version>/` on, and one fixed stand-in checkout root for a path with a `dnbg-workflow/` component anywhere else, keeping the tail from `dnbg-workflow/` on; a block naming no plugin path is dropped, and `cwd` is dropped, since nothing reads it with R10 retired, so no command text, prompt or tool output is committed. The sweep recognises the installed path as `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/plugins/cache/<marketplace>/dnbg-workflow/<version>/` (C17), so a test supplies its own installed tree by setting `CLAUDE_CONFIG_DIR` and substituting that directory for the `<config>` stand-in when it copies the fixture in, as `tests/context-size.bats` copies its fixture under a config directory of its own; both R19 branches then have a fixture case.
- **R12.** For any session that has a usage record (R1), the sweep's figures, counted over each transcript up to the point the record was taken, equal that record's `requests` and four counts. An agent keeps making requests after taking its record, writing its retrospective and its report among them, so the sweep's row over the whole transcript is the higher figure ([654-D2](https://github.com/dbaggott/claude-plugins/issues/654#issuecomment-6567052619)). *(end-to-end: A2)*
- **R18.** `process-review` step 1 excludes `<root>/_usage/` as it excludes `_reviews/`, shipped with the sweep, so no run between the sweep (https://github.com/dbaggott/claude-plugins/issues/659) and the process-review child (https://github.com/dbaggott/claude-plugins/issues/660) reads a sweep report as an unreadable retrospective.
- **R19.** The sweep counts a read of a plugin file only when the path is under the installed plugin (C17), recording it plugin-relative, below `<version>/`. A read of the same file at any other path, such as a checkout, counts under `ignored_reads` and nowhere else, so a session developing the plugin keeps its usage rows and inflates no read count. A directory under the installed copy is not a file read, since `ignored_reads` needs a file, and a path named twice in one tool use is one read ([659 row](https://github.com/dbaggott/claude-plugins/issues/659#issuecomment-6565964981)).

### The process review

- **R13.** `process-review` step 1 also gathers each batch file's `usage` frontmatter and the newest `_usage/` report, and its description names both as inputs, replacing C9's "only the retrospective files and its own past reports". In a `delta` run, usage is counted only from files stamped after the chained report's `newest` plus the files it listed as Unreadable, so no file's usage is summed twice ([660-D1](https://github.com/dbaggott/claude-plugins/issues/660#issuecomment-6566241487)).
- **R14.** The report gains a `## Usage` section: a table keyed by the retrospective's `role`, of sessions, requests and the four counts, built by summing `scope=self` records per `role` and `scope=session` records as per-issue totals, never adding one kind to the other, with a `scope=session` record's `child=` lines shown under the owner's row by `agent` and `depth` and summed into no role; the same table from the chained report beside it, so the change is visible; and the sweep report's per-role figures cited by path, quoting its rows for `main` and every agent type starting `dnbg-workflow:` ([660-D2](https://github.com/dbaggott/claude-plugins/issues/660#issuecomment-6566227870)). Under the section, the files listed as lacking usage are only those whose usage the run counts, so a delta run does not re-list files outside R13's counted window ([660-D1](https://github.com/dbaggott/claude-plugins/issues/660#issuecomment-6566380050)). Raw counts only; a weighted figure, if given, names its weights and the model they price.
- **R15.** The `## Read but not used` heading is tallied per named file across the batch, and a file named by two or more sources is listed as a split candidate under that section, in the pattern form step 3 already uses.
- **R16.** Whether a usage pattern becomes a drafted issue in step 4 follows Q2's default until the operator sets a threshold.
- **R17.** Every role's close-out writes a usage record and every `scope=session` close-out posts a `Usage:` comment, observed on a real run. *(end-to-end: A1)*

## Decisions

- **D1. Each role reports the usage it incurred, at its own close-out, and a session owner additionally reports the whole session with one subtotal per transcript under it; the `scope` tag tells the two apart. A `scope=self` record is the agent's own transcript only; the agents it dispatched are the session owner's `child=` lines, carrying their depth and parent.** Because: a rule keyed on the role rather than on how it was invoked is one sentence that every close-out already routes through (C8), the per-role record is then one shape summed by role rather than joined across files, and the owner's session total is the only source of its own overhead, which 615 exists to control. Revisit if: the harness gives a dispatched agent its own identity or transcript path, which removes the nonce without changing the rule.
- **D2. Self-identification is the two-call nonce of C5, failing to `UNKNOWN` on zero or several matches.** Because: no documented variable names a dispatched agent (C4), the running call is not logged before it runs (C5), and a wrong file would attribute a parent's usage to a child silently. Revisit if: a documented identity appears, per D1's condition.
- **D3. Records hold raw token counts, never a weighted cost.** Because: the counts are observed and a weighting is a model whose inputs, price ratios and model mix, change under it; a report that weights names its weights where the reader can see them. Revisit if: none identified.
- **D4. Usage goes in the retrospective's frontmatter, not under a heading.** Because: `process-review` groups free text by heading and reads structured fields from frontmatter already (`role`, `issue`); numbers belong with the structured fields, and the headings stay pinned (C10), five since R8. Revisit if: `process-review` moves to a store other than the files.
- **D5. The session owner also posts the session line on the issue as a `Usage:` comment.** Because: the issue is the only join across an orchestrator restart (C12) and a reviewer in its own session, and a comment is queryable with `gh` where a local file is not. Revisit if: the comments are judged noise, in which case the line moves into the close-out report the owner already posts and the join is lost.
- **D6. The sweep ships inside the plugin, in Bash with `jq`, like every other script (C14), rather than as the audit's Python.** Because: `process-review` runs it from the installed plugin, CI already lints and tests Bash, and the audit's Python is a prototype to be read, not shipped. Revisit if: the Bash and `jq` version cannot process a month of transcripts in acceptable time, measured in the child.
- **D7.** *Retired 2026-11-01: excluding whole sessions removed real usage and the A1 run (654-B11); superseded by D10.* **The sweep excludes sessions working in the plugin's own checkout.** Because: the audit found those sessions inflate reads of plugin files, since reading a skill to edit it looks like reading it to follow it. Revisit if: a project slug for the checkout cannot be told apart from an installed plugin's reads.
- **D10. The sweep counts plugin-file reads only at the installed path, and excludes no session.** Because: the inflation the audit found was in read counts, from reading a skill in order to edit it, and the audit's own correction was to count reads of the installed copy; a session developing the plugin still pays real usage, and A1's run was planned for that checkout, though it was made in a testbed ([654-D1](https://github.com/dbaggott/claude-plugins/issues/654#issuecomment-6566650790)). Revisit if: the plugin is used from a checkout rather than an install, which the installed path cannot see.
- **D8. No per-PR size gate or ratchet.** Because: growth in prose is the normal case in this repo, the friction would land on every PR, and the measurement loop is the instrument meant to catch growth that matters. Revisit if: two consecutive `process-review` reports show growth the loop reported and nothing acted on.
- **D9. `process-review` runs the sweep itself, as a step, rather than a new skill owning it.** Because: one script does not warrant a skill, and the cadence is `process-review`'s. Revisit if: the sweep acquires operator-facing choices of its own.

## Open questions

- **Q1. What is the script called?** Built at its default: `session-usage.sh`, because it sits beside `context-size.sh` and names what it measures.
- **Q2. What usage change is worth drafting an issue?** Built at its default: no numeric threshold in the first version; the `## Usage` section shows the table and the chained report's table, and drafting is a judgement that quotes both, because no baseline exists until the first report and a threshold set before it would be invented.
- **Q3. How often does the sweep run?** Built at its default: whenever `process-review` runs, with a monthly floor the operator keeps, because transcripts are local and nothing can schedule it remotely.
- **Q4. Do the spec roles, `spec-author` and `issue-reviewer`, record usage too?** Built at its default: yes, because R5 is one rule for every close-out and an exception would need its own text in two more places.
- **Q5. Which Bash commands count as a read of a plugin file?** Built at its default: any Bash `command` whose text names a path under the installed plugin, whatever the command, because agents read with `cat`, `sed -n`, `head` and `grep -n` alike and the path is what identifies the read.

## End-to-end acceptance criteria

- **A1.** One real orchestrated run of a plain issue, author and reviewer dispatched, after the children are installed: the orchestrator's retrospective frontmatter carries `scope: session` whose `children` list contains, at depth 1, entries whose `agent` values are `dnbg-workflow:author-orchestrated` and `dnbg-workflow:reviewer-orchestrated`, and may contain deeper entries the author's self-review dispatched; the author's and reviewer's retrospectives carry `scope: self` with those `agent` values; the issue carries one `Usage:` comment, posted under the `orchestrator` role, whose lines equal the orchestrator's frontmatter.
